## 1. Core design ("network of networks") and component glossary

### Takeaway
Canton is not one replicated chain: it separates *coordination* (synchronizers that order encrypted messages) from *storage and execution* (participant nodes that hold only their own parties' contracts). The "Canton Network" is the set of all participant nodes and synchronizers that can interoperate; the Global Synchronizer is the one decentralised, publicly reachable synchronizer run by Super Validators.

### Cited Findings
- **[OFFICIAL] Design principle.** "Canton separates coordination from storage. Synchronizers coordinate transaction ordering; participant nodes (validators) store data for their hosted parties… Unlike Ethereum where every node stores all state, Canton nodes store only their parties' data. The synchronizer coordinates but never stores transaction content." — [Architecture Overview](https://docs.canton.network/overview/learn/architecture)
- **[OFFICIAL] "Network of networks".** The Jan-2024 whitepaper defines the Canton Network as "a smart contract network of networks" in which "each application provider [can] define their application's privacy, scaling, permissions, and governance while being part of a broader decentralized public permissioned network"; a "virtual global ledger" exists only as the union of per-party views. — [Canton Network whitepaper (updated Jan 2024)](https://www.canton.network/hubfs/Canton/Canton%20Network%20-%20White%20Paper.pdf)
- **[OFFICIAL] Party** = on-ledger identity (analogous to an address/EOA) with ID format `name::fingerprint` where the fingerprint is a hash of a public key, e.g. `alice::1220f2fe…`. Parties "have costs associated with creation and create state on validators" (not ephemeral). **Local party**: keys held by the validator, which signs on the party's behalf. **External party**: keys held outside; every transaction needs an explicit signature. — [Core Concepts](https://docs.canton.network/overview/understand/core-concepts)
- **[OFFICIAL] Participant node** = "the private, self-sovereign computational and storage unit for an entity"; it hosts parties, stores their contracts (the **Active Contract Set, ACS** = set of currently non-archived contracts), executes Daml, validates, and exposes the Ledger API. **Validator** = "the Canton Network role that operates a participant node"; concretely a participant node plus the Splice *validator app* (wallet, traffic top-up, onboarding automation). — [Architecture Overview](https://docs.canton.network/overview/learn/architecture); [Core Concepts](https://docs.canton.network/overview/understand/core-concepts)
- **[OFFICIAL] Synchronizer** = sequencer(s) + mediator(s). **Sequencer**: "authenticated, timestamped multicast"; total order per synchronizer; forwards opaque encrypted payloads; enforces traffic limits. **Mediator**: coordinator of the two-phase commit; collects approve/reject responses and issues the verdict; sees informee lists and results but not payloads. "Participants and mediators never communicate directly with each other. All protocol messages flow through sequencers." **Member** = any sequencer, mediator or participant node of a synchronizer. — [Ordering Consensus](https://docs.canton.network/overview/reference/ordering-consensus); [Canton Protocol Specification](https://docs.canton.network/overview/reference/canton-protocol-specification)
- **[OFFICIAL] Global Synchronizer (GS)** = "a synchronizer instance (BFT configuration of several sequencer + mediator nodes) operated by multiple independent parties"; it "is not a separate blockchain", "is not a separate storage layer", and "is not required for all Canton applications". Governed by the Canton Foundation "under Linux Foundation". — [The Global Synchronizer](https://docs.canton.network/overview/understand/global-synchronizer)
- **[OFFICIAL] Super Validator (SV)** runs "everything a regular validator runs, plus the Global Synchronizer infrastructure and governance tooling": sequencer node (with the CantonBFT orderer in-process), mediator node, SV app (governance), Scan app (public index/explorer API), validator app, participant, four PostgreSQL databases; Kubernetes is mandatory. "There is no partial SV deployment." — [Super Validator Components](https://docs.canton.network/overview/reference/super-validator-components)
- **[OFFICIAL] DSO (Decentralized Synchronizer Operator)** = the collective of SVs operating nodes; the **DSO party** is a decentralised party used to sign joint actions. — [Glossary](https://docs.canton.network/overview/understand/glossary)
- **[OFFICIAL] Splice** = "the open-source project (under Hyperledger Labs) providing infrastructure for operating, funding, and governing decentralized Canton synchronizers" — it implements Canton Coin, the validator app, wallet, Scan, and governance apps. The docs now link the code at `github.com/canton-network/splice`. — [The Global Synchronizer](https://docs.canton.network/overview/understand/global-synchronizer); [SDKs & Tools overview](https://docs.canton.network/sdks-tools/overview)
- **[OFFICIAL] Daml ledger model.** State is a set of immutable contracts (instances of Daml templates); a contract can only be created or archived, never mutated. Docs and CIP-0056 call this an "extended Unspent-Transaction-Output (UTXO) model" with "a one-to-one correspondence between Daml contracts and UTXOs", where UTXOs "are annotated with their stakeholders and are only distributed to the nodes hosting these stakeholders". — [Core Concepts](https://docs.canton.network/overview/understand/core-concepts); [CIP-0056](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0056/cip-0056.md)
- **[OFFICIAL] Four environments.** LocalNet (local Docker), DevNet (VPN + SV sponsorship), TestNet (application), MainNet (full onboarding). All three shared nets are run by the same SVs. "MainNet has never been reset and is not expected to be." — [The Global Synchronizer](https://docs.canton.network/overview/understand/global-synchronizer); [docs full text](https://docs.canton.network/llms-full.txt)
- **[OFFICIAL] Timeline.** Global Synchronizer TestNet June 2023; MainNet "went live in June 2024" per the MiCA whitepaper (the Canton Coin whitepaper is dated July 2024). — [Canton Coin MiCA whitepaper](https://www.canton.network/hubfs/Canton%20Network%20Files/whitepapers/Canton%20Coin%20%20-%20MiCA%20Whitepaper.pdf)
- **[OFFICIAL] Access is sponsored, not open.** A new validator needs sponsorship by an SV (onboarding secret); the canton.network FAQ says "Anyone can request a validator node (currently sponsorship is needed)". — [The Global Synchronizer](https://docs.canton.network/overview/understand/global-synchronizer); [canton.network FAQ](https://www.canton.network/faq)

### Inferences
- The closest mental model is "many private per-stakeholder state machines + shared ordering services", not "one chain with private data". The term "L1" used in marketing refers to the union of all synchronizers and participants, not to a single ledger.
- "Validator" in Canton does not mean "consensus node of the whole network" as on Ethereum/Solana: a Canton validator validates only transactions in which its hosted parties are stakeholders. Only SVs take part in ordering consensus.

### Gaps
- Exact date of the Global Synchronizer Foundation → Canton Foundation rename was not found in a primary source (canton.foundation assets date from October 2025; a December 2025 blog still linked `github.com/global-synchronizer-foundation/cips`).
- Splice's formal status at Hyperledger Labs vs. the newer `canton-network` GitHub organisation could not be verified (github.com is blocked from this machine).

## 2. Transaction flow and the two-phase commit / confirmation protocol

### Takeaway
A transaction is interpreted once by the submitter, cut into per-action encrypted *views*, ordered by the sequencer, re-executed and confirmed only by participants hosting the affected stakeholders, and committed when the mediator announces an all-or-nothing verdict. Finality is the sequenced verdict: no forks, no re-orgs.

### Cited Findings
- **[OFFICIAL] Five phases.** (1) Preparation, (2) Submission, (3) Sequencing & Distribution, (4) Validation & Confirmation, (5) Aggregation & Commit. "No single node ever sees the full transaction in the clear." — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Phase 1 – Preparation.** The submitting participant receives a command via the Ledger API, executes the Daml code against its local ACS and builds a *transaction tree* (creates, exercises, fetches and their consequences). It computes **informees** per action node (signatories, observers, actors), turns "each action node … [into] a separate view", encrypts each view for the participants hosting its informees, and computes a **root hash** that commits to the whole tree. — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] View encryption scheme.** (a) a short-lived symmetric **session key** is generated per distinct recipient group; (b) the serialised Merkle tree of each view is encrypted with it; (c) the session key is encrypted with the public key of each participant hosting an informee. Parent views carry the hashes *and encryption keys* of their direct sub-views, so whoever can open a parent can open its children. The hierarchical views form "a Merkle-like tree, where the hashes commit to the contents of the hidden nodes and subtrees without revealing the content". — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Phase 2 – Submission.** One *confirmation request batch* goes to the sequencer containing: encrypted views (one per action node), **root hash messages** (one per recipient participant), and **informee messages** for the mediator (informee list + confirmation policy per view). — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Phase 3 – Sequencing.** The sequencer does a "BFT-write": ordering nodes agree on position and timestamp (**sequencing time / record time**), then deliver each message only to its designated recipients. The mediator starts a deadline timer. — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Phase 4 – Validation.** Each confirming participant checks: **conformance** (re-executes the Daml logic; result must match), **authorization** (required signatories/controllers), **consistency** (input contracts still active in its ACS — the double-spend check), **time bounds** (ledger time vs. record time within a synchronizer-defined tolerance), **root hash** (its view belongs to the same tree as everyone else's — detects equivocation by the submitter). It then sends a signed **mediator response** (approve/reject) via the sequencer. — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Phase 5 – Verdict.** The mediator applies a **signatory-based confirmation policy**: every signatory of every affected contract must be confirmed by at least its *confirmation threshold* of hosting participants (m-of-n for multi-hosted parties). "A single signatory failing its threshold is enough to reject the entire transaction." Observers receive views but their confirmation is not required. The verdict (**transaction result**) is sequenced and delivered; participants then atomically apply or discard. — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle); [Smart Contract Consensus](https://docs.canton.network/overview/reference/smart-contract-consensus)
- **[OFFICIAL] Finality.** "Once the verdict is sequenced and delivered, the transaction result is final. There are no forks, reorganizations, or rollbacks." — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Timeouts.** Decision time = sequencing time + synchronizer decision timeout; the "maximum decision duration" is the sum of `confirmationResponseTimeout` and `mediatorReactionTimeout`, "with a default of 30 seconds each". If confirmations are missing at the deadline the transaction is rejected by timeout. — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle); [docs full text (synchronizer operations)](https://docs.canton.network/llms-full.txt)
- **[OFFICIAL] Why "two-phase commit".** Canton frames every contract as belonging to a *channel* (its stakeholder group) that runs state-machine replication; a transaction spanning several channels uses classical 2PC (prepare = confirmation request, commit/abort = mediator verdict) so all channels commit or none do. "Mediator = Two-phase commit coordinator." — [Canton Protocol Specification](https://docs.canton.network/overview/reference/canton-protocol-specification); [Synchronizer overview](https://docs.canton.network/overview/reference/synchronizer-overview)
- **[OFFICIAL] Failure modes.** Preparation failure (rejected locally, nothing sent), validation rejection, timeout, equivocation detection. "In all failure cases, no state is changed." — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Mediator selection on the GS.** "Each SV runs both a sequencer and a mediator. The mediator for a given transaction is determined by the sequencer that first processes the transaction's confirmation request." Mediators on the GS "use BFT state machine replication". — [Global Synchronizer Architecture](https://docs.canton.network/overview/learn/global-synchronizer-architecture); [Super Validator Components](https://docs.canton.network/overview/reference/super-validator-components)
- **[OFFICIAL] Submitter needs the inputs.** "Constructing transactions requires access to all UTXOs referenced or consumed by the transaction"; wallets read them from their own validator and registries serve registry-private contracts over off-ledger HTTP APIs (explicit contract disclosure). — [CIP-0056](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0056/cip-0056.md)

### Inferences
- A committed transaction costs at least three sequenced message rounds (request, responses, verdict), each paying ordering latency; this is why end-to-end latency is hundreds of milliseconds to seconds rather than single-block time.
- Liveness for any given contract depends on its signatories' participants being online: an offline counterparty validator blocks transactions on shared contracts until timeout (mitigated by multi-hosting with thresholds).

### Gaps
- The Global Synchronizer's actual configured values for `confirmationResponseTimeout`, `mediatorReactionTimeout` and ledger-time tolerance were not found (only Canton defaults and one example config with 40 s / 20 s).
- The GS mediator-group threshold (how many SV mediators must agree on a verdict) is not stated numerically in the docs fetched.

## 3. Sub-transaction privacy: who sees what, "need-to-know", "Proof of Stakeholder", and trade-offs

### Takeaway
Privacy in Canton comes from *not distributing data* (selective, encrypted delivery of views), not from zero-knowledge proofs. Stakeholders and their hosting validators see plaintext; sequencers see ciphertext plus routing metadata; mediators see who must confirm; nobody else sees anything. The price is no global state, no public verifiability, and reliance on your own validator and on the mediator's honesty.

### Cited Findings
**Visibility matrix (official sources)**
- **[OFFICIAL] Signatory**: "Always sees the contract and all its events"; must authorise creation; its participant must confirm. **Observer**: sees the contract by explicit declaration; confirmation not required. **Controller**: sees the choices it can exercise. **Stakeholder** = signatories + observers. — [Privacy Model Explained](https://docs.canton.network/overview/learn/privacy-model); [Core Concepts](https://docs.canton.network/overview/understand/core-concepts)
- **[OFFICIAL] Two visibility principles.** (1) parties see actions they have a stake in; (2) "Parties who see an action see its consequences" (so they can verify it). — [Privacy Model Explained](https://docs.canton.network/overview/learn/privacy-model)
- **[OFFICIAL] Divulgence.** When a transaction fetches/uses a contract, parties to that transaction "may learn about [it]… This 'divulgence' is automatic" even if they were never observers — flagged by the docs as a common privacy mistake. Participants hosting such **witnesses** also receive the encrypted view. — [Privacy Model Explained](https://docs.canton.network/overview/learn/privacy-model); [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Hosting validator.** "Your hosting validator sees all your data. Choose your validator carefully—this is a trust relationship." — [Core Concepts](https://docs.canton.network/overview/understand/core-concepts)
- **[OFFICIAL] Non-stakeholder validators.** "A participant that hosts no informees for any view in the transaction receives nothing and learns nothing about the transaction." — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Sequencers (i.e. Super Validators on the GS).** "They see metadata — recipient lists and message sizes — but not transaction content." They also persist the encrypted views "for a limited period" and cannot decrypt "unless [they know] the private key of one of the informee participants". Recipients do not learn the sender's identity ("sender privacy"). — [Ordering Consensus](https://docs.canton.network/overview/reference/ordering-consensus); [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle)
- **[OFFICIAL] Mediators (also SVs on the GS).** "Mediators see informee lists (which parties are involved in which transaction views) and the confirmation results (approve/reject per view). They do not see the encrypted transaction payloads." — [Ordering Consensus](https://docs.canton.network/overview/reference/ordering-consensus)
- **[OFFICIAL] What the public sees.** Canton Coin activity that involves the DSO party is indexed by every SV's Scan app (balances, transfers, mining rounds, rewards); "reward distributions and Canton Coin fees are published". Application contracts not involving the DSO are not in Scan. — [Super Validator Components](https://docs.canton.network/overview/reference/super-validator-components); [canton.network FAQ](https://www.canton.network/faq)
- **[OFFICIAL] Residual leakage acknowledged.** Docs list "Timing attacks" (when transactions occur, sizes, activity patterns) as a privacy risk, and say a dedicated synchronizer lets you "hedge the 'harvest now, decrypt later' quantum threat by keeping your contracts on a dedicated synchronizer". — [Privacy Model Explained](https://docs.canton.network/overview/learn/privacy-model); [Dedicated Synchronizers](https://docs.canton.network/global-synchronizer/extension-synchronizers/dedicated-synchronizers)

**"Need-to-know" and "Proof of Stakeholder"**
- **[OFFICIAL] Need-to-know.** "The submitting participant sends these views via the synchronizer's sequencer to all involved participants on a need-to-know basis… a participant receives only the data for the witnesses it hosts, not all of the transaction." CIP-0056 repeats: "information about asset holdings and transfers is shared on a need-to-know basis". — [Transaction Lifecycle](https://docs.canton.network/overview/reference/transaction-lifecycle); [CIP-0056](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0056/cip-0056.md)
- **[OFFICIAL] Proof of Stakeholder.** "Only the participant nodes hosting parties with a stake in the affected contracts participate in validation and confirmation. No global replication of state or computation is required." It is the *first* of two consensus layers (2PC among stakeholders); the *second* is BFT ordering. It is not stake-weighted: "stake" means being a signatory/observer of the contract, not holding tokens. — [Smart Contract Consensus](https://docs.canton.network/overview/reference/smart-contract-consensus); [Two-Layer Consensus](https://docs.canton.network/overview/learn/two-layer-consensus); [MiCA whitepaper §H.4](https://www.canton.network/hubfs/Canton%20Network%20Files/whitepapers/Canton%20Coin%20%20-%20MiCA%20Whitepaper.pdf)
- **[OFFICIAL] Trust statement.** "As long as your validators are honest, your counterparties cannot finalize invalid transactions involving you." Shaul Kfir (Digital Asset co-founder): "In Canton, as in all other blockchains, I only trust my own validator and assume anyone else can be malicious." — [Trust Model Overview](https://docs.canton.network/overview/learn/trust-model); Kfir quote **[SNIPPET]** via [Cointelegraph, 21 Apr 2026](https://cointelegraph.com/news/canton-zksync-clash-blockchains-enforce-rules)

**Difference from global-state chains and from ZK privacy**
- **[OFFICIAL] vs. Ethereum-style chains.** Canton's own comparison table: validation "Only stakeholder participants" vs "All nodes"; state storage "Only hosting participants" vs "All nodes"; finality "Mediator verdict (immediate)" vs "Block confirmation"; message distribution "Sequencer multicast (encrypted)" vs "Gossip (public)". — [Smart Contract Consensus](https://docs.canton.network/overview/reference/smart-contract-consensus)
- **[OFFICIAL] vs. ZK.** "Canton does not use zero-knowledge proofs. Instead, privacy is achieved through selective data distribution… without ZK circuit complexity or proof generation overhead." Official critique of ZK: proof cost, circuit complexity/auditability, limited expressiveness, trusted setups. — [Module 2: privacy differences](https://docs.canton.network/appdev/modules/m2-privacy-differences); [The Problem](https://docs.canton.network/overview/understand/the-problem)
- **[OFFICIAL] vs. Fabric channels.** Granularity is "sub-transaction level" vs "channel-level"; cross-channel atomicity is native. — [Module 2: privacy differences](https://docs.canton.network/appdev/modules/m2-privacy-differences)
- **[INDEPENDENT][SNIPPET] L2BEAT ("Canton vs Prividium").** Canton "protects confidentiality against infrastructure but leaves integrity to trust"; a compromised mediator with threshold 1 can issue a false verdict, and replicating mediators "only shifts the assumption to a majority of honest mediators"; when assumptions fail "the protocol has no in-band mechanism to catch it". L2BEAT calls the mediator "Canton's most consequential design choice". — [L2BEAT publication](https://l2beat.com/publications/canton-vs-prividium); echoed by [TACEO analysis](https://core.taceo.io/articles/onchain-privacy-models/)
- **[OFFICIAL] concession.** Yuval Rooz (Digital Asset CEO) conceded in an April 2026 debate that Canton "does not have public verifiability", adding there are plans to introduce it. — **[SNIPPET]** [Cointelegraph, 21 Apr 2026](https://cointelegraph.com/news/canton-zksync-clash-blockchains-enforce-rules)

**Trade-offs: no global state, data availability, pruning, GDPR**
- **[OFFICIAL] No global state.** "There is no shared global state that could be queried or leaked." Consequence in the token standard: `totalSupply` and registry-private UTXOs must be served by registries over off-ledger HTTP APIs. — [Smart Contract Consensus](https://docs.canton.network/overview/reference/smart-contract-consensus); [CIP-0056](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0056/cip-0056.md)
- **[OFFICIAL] Fork detection without global state: ACS commitments.** Participants periodically exchange signed pairwise summaries of their shared active contracts; a mismatch signals divergence. On the GS the interval `acsCommitmentReconciliationInterval` defaults to 30 minutes. Protocol version 36 (Canton 3.6) re-implemented the pipeline (digest processor / sender / matcher) to decouple validator memory from the number of hosted parties. — [Pruning](https://docs.canton.network/overview/reference/pruning); [Canton 3.6.1 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-6-1); [Splice release notes](https://docs.canton.network/global-synchronizer/release-notes/splice)
- **[OFFICIAL] Pruning.** Every node may "forget a prefix of the history, and instead store a state snapshot"; "pruning never removes active … contracts". A participant prunes at time *t* only with matching commitments from every counter-participant (non-repudiation), unless it opts out for specific counterparties. Long-term history can be kept in PQS. — [Pruning](https://docs.canton.network/overview/reference/pruning)
- **[OFFICIAL] GDPR / HIPAA.** Pruning is explicitly motivated by regulation: "to comply with the General Data Protection Regulation (GDPR)… Canton operators must declare reasonable retention periods and make sure that the data is deleted afterwards". The 2020 protocol paper already claimed Canton "allows developers to balance auditability requirements with the right to forget". — [Pruning](https://docs.canton.network/overview/reference/pruning); [Canton protocol whitepaper (2020)](https://www.canton.network/hubfs/Canton/canton-whitepaper.pdf)
- **[OFFICIAL] Auditability patterns.** Add a regulator/auditor as observer, or expose a non-consuming "Audit" choice; "Audit trails are cryptographically signed". — [Privacy Model Explained](https://docs.canton.network/overview/learn/privacy-model); [Trust Model Overview](https://docs.canton.network/overview/learn/trust-model)

### Inferences
- There is an internal tension in the official wording: the privacy page says "The synchronizer sees none of this — only encrypted messages and confirmation results" and "No metadata leakage", while the protocol reference states that sequencers see recipient lists and sizes and mediators see per-view informee party lists. Precisely: payload confidentiality holds against SVs, but **transaction-graph metadata (who transacts with whom, when, how big) is visible to SV sequencers/mediators** on the Global Synchronizer.
- Because ciphertext transits SV infrastructure, long-term confidentiality depends on the asymmetric encryption scheme surviving; the docs' own "harvest now, decrypt later" remark confirms this is a recognised risk.
- Data availability is a per-stakeholder responsibility: if all participants hosting a contract's stakeholders lose it (or prune history), no one else can reconstruct it. This is by design (GDPR-compatible) but is the opposite of a public chain's guarantee.
- Integrity for a third party who is *not* a stakeholder is not verifiable at all today; this is exactly the gap ZK-based "verify without seeing" designs target.

### Gaps
- No primary document found that quantifies metadata exposure to SVs (e.g. whether party IDs or only participant IDs are visible to sequencers, retention period of ciphertext on GS sequencers).
- No published design or timeline for the "public verifiability" Rooz mentioned.
- Full L2BEAT, TACEO, 4pillars and Halborn texts could not be fetched; only search summaries were available.

## 4. Global Synchronizer consensus: BFT ordering, CometBFT → CantonBFT, number of Super Validators, fault threshold, decentralisation path

### Takeaway
As of November 2026 the Global Synchronizer orders messages with **CantonBFT** (Canton's own ISS/Narwhal-inspired, multi-leader PBFT-style orderer running inside each SV's sequencer); it replaced single-leader **CometBFT** via a Logical Synchronizer Upgrade in roughly October 2026. Classical BFT bounds apply (tolerates f < n/3). The MainNet config lists **13 SV node identities (11 distinct organisations)**, while "Super Validator" status with reward weight has been granted by CIP to roughly 50+ organisations that mostly do not run their own consensus node.

### Cited Findings
- **[OFFICIAL] Current orderer.** "The Global Synchronizer uses CantonBFT, Canton's native BFT ordering service, which runs in-process with each SV's sequencer node." Splice 0.10.2 "Removed the remaining CometBFT support from the SV app and UI… Helm charts, docker images". — [Super Validator Components](https://docs.canton.network/overview/reference/super-validator-components); [Splice release notes](https://docs.canton.network/global-synchronizer/release-notes/splice)
- **[OFFICIAL] History.** TestNet moved from a Postgres-backed domain to CometBFT in October 2023 ("The global domain now uses CometBFT"); CometBFT 0.37.x was used through 2025–26. Canton 3.5.1 (27 May 2026) shipped "DA BFT" in beta; Canton 3.5.15 (27 Aug 2026) declared "CantonBFT is now GA for dedicated synchronizers… currently undergoing Canton Network production testing"; Splice 0.8.0: "The protocol version remains 35, but the ordering layer has been prepared for a switch from CometBFT to CantonBFT. This switch will require an LSU. The LSU … on DevNet has already taken place." — [Splice release notes](https://docs.canton.network/global-synchronizer/release-notes/splice); [Canton 3.5.15 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-5-15)
- **[SNIPPET] MainNet cutover date.** A forum plan tentatively set the MainNet CantonBFT LSU for 8 Aug 2026; a BitGo status entry and a Bitrue article place the actual MainNet LSU "to adopt CantonBFT" in October 2026 (Bitrue dated 14 Oct 2026). — [Canton forum thread](https://forum.canton.network/t/canton-3-4-to-canton-3-5-transition/8777); [BitGo status via isdown.app](https://isdown.app/status/bitgo/incidents/667674-canton-scheduled-network-upgrade-lsu); [Bitrue](https://www.bitrue.com/blog/canton-network-activates-mainnet)

This is a small, known, contractually bound set — a consortium-BFT security model, not an open-membership one.
- Marketing headlines of "55+ Super Validators" describe reward/governance-weight holders; the number of *independently operated consensus nodes* is what matters for BFT and is 13. Whether weight-holding SVs hosted under the Foundation node each have an independent governance vote was not resolved (one press report says "equal voting power"; CIP weights say otherwise for rewards).
- Decentralisation is evolving along three axes rather than by opening the SV set: (a) stake-like locking tied to SV weight, (b) multi-hosting/confirming-validator incentives at the party level, (c) permissionless *dedicated* synchronizers. Nothing found proposes permissionless entry to the Global Synchronizer's ordering set.

## 5. Atomic cross-application / cross-synchronizer composition (reassignment, atomic DvP)

### Takeaway
Atomicity exists *within one synchronizer*: a single Daml transaction can touch contracts of many apps and parties and commits all-or-nothing. Across synchronizers there is no atomic commit; instead contracts are first *reassigned* (non-atomically, two steps) to a common synchronizer, and the settlement transaction is atomic there. In practice the Global Synchronizer is the common venue.

### Cited Findings
- **[OFFICIAL] Hard rule.** "A Daml transaction executes on a single synchronizer, i.e., all input contracts must be assigned to this synchronizer." — [Multi-synchronizer](https://docs.canton.network/overview/learn/multi-synchronizer)
- **[OFFICIAL] Reassignment = unassign + assign.** Step 1: submitter obtains a *time proof* (target timestamp) from the target synchronizer, then an **unassignment** is sequenced/confirmed on the source; the contract becomes inactive ("pending assignment"). Step 2: an **assignment** on the target makes it active there. A **reassignment counter** increments per move. Confirmers are *signatory* reassigning participants connected to both synchronizers. — [Reassignment Protocol](https://docs.canton.network/overview/reference/reassignment-protocol)
- **[OFFICIAL] Not atomic, but no settlement risk.** "The reassignment steps… are each two-steps and occur in their own transactions… If the assignment fails (for example, due to a topology change), the contract remains pending until the situation is resolved." "The settlement step is atomic… There is no state where Alice has paid cash but not received securities." — [Cross-Synchronizer DvP Example](https://docs.canton.network/overview/reference/cross-sync-dvp-example)
- **[OFFICIAL] Worked DvP.** Cash on a Payments synchronizer and Securities on a Securities synchronizer are both reassigned to a Settlement synchronizer (e.g. the GS), swapped in one Daml transaction, optionally reassigned back. — [Cross-Synchronizer DvP Example](https://docs.canton.network/overview/reference/cross-sync-dvp-example)
- **[OFFICIAL] Automatic vs explicit.** The participant's **synchronizer router** can auto-reassign inputs to the best common synchronizer (highest priority, fewest reassignments, lowest ID as tie-break); apps can also issue explicit unassign/assign commands. Warning: "Both unassignment and assignment lock the contract, which means reassignments compete with other workflows, including read-only transactions." — [Reassignment Protocol](https://docs.canton.network/overview/reference/reassignment-protocol)
- **[OFFICIAL] No cross-synchronizer clock.** "Because time cannot be compared across synchronizers, there is no global causality guarantee on the updates stream." — [Reassignment Protocol](https://docs.canton.network/overview/reference/reassignment-protocol)
- **[OFFICIAL] Maturity.** Canton 3.5.1 (May 2026): "Multi-synchronizer support is available in early access… should only be used in test environments" (alpha flag required on all stakeholder participants). Canton 3.7.0 (29 Oct 2026): from **protocol version 37** the `EnableMultiSynchronizer` flag "is no longer needed"; any stakeholder may submit the assignment; participants auto-complete others' reassignments after 60–120 s; reassignment traffic-cost estimation added. — [Canton 3.5.1 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-5-1); [Canton 3.7.0 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-7-0)
- **[OFFICIAL] MainNet protocol version.** The MainNet LSU of 7 Nov 2026 moved the physical synchronizer ID from `::35-6` to `::36-7` (protocol version 36, serial 7). — [Recovering stuck validators after the November 2026 LSU](https://docs.canton.network/global-synchronizer/production-operations/validator-recovery-november-2026-lsu)
- **[OFFICIAL] Token-standard DvP (single synchronizer).** CIP-0056 allocations: each party's wallet locks holdings into an *allocation* for a settlement with a deadline; once all legs exist the settlement app (*executor*) submits "the one Daml transaction that triggers all of the transfers… either all transfers settle or none". CIP-0056 recommends registries connect to the GS because it is "the most likely synchronizer that all input contracts of a settlement transaction can be assigned to". — [CIP-0056](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0056/cip-0056.md)
- **[OFFICIAL] Whitepaper condition.** "Canton allows cross-subnet transactions only whenever there exists at least one sync domain to which all transaction participants are connected." — [MiCA whitepaper §H.2](https://www.canton.network/hubfs/Canton%20Network%20Files/whitepapers/Canton%20Coin%20%20-%20MiCA%20Whitepaper.pdf)
- **[OFFICIAL] Economics of dedicated synchronizers.** CIP-0129 (approved 23 Oct 2026) and CIP-0132 (approved 24 Nov 2026) bring dedicated synchronizers into the CC burn economy via a trusted "paymaster" who burns CC post-hoc on the GS based on traffic reports; "SVs cannot see traffic on synchronizers they do not operate". — [CIP-0129](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0129/cip-0129.md); [CIP-0132](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0132/cip-0132.md)

### Inferences
- Since MainNet runs protocol version 36 (as of the 7 Nov 2026 LSU) and flag-free multi-synchronizer needs version 37, **production cross-synchronizer reassignment on MainNet is still effectively pre-GA in November 2026**; another LSU (to PV 37, Splice 0.10.x) is the prerequisite. "Atomic composability across the whole network" therefore currently means "atomic on the Global Synchronizer".
- Cross-synchronizer DvP trades atomic cross-chain commit for a *lock-and-move* design: the risk is liveness (a contract stuck "pending assignment"), not loss of funds.

### Gaps
- No public data on how many dedicated synchronizers run production workloads or on reassignment volumes.
- Scheduled date of the MainNet LSU to protocol version 37 (kept on the dynamic SV operations calendar `sv-cal.canton.foundation`, not readable here).

## 6. Daml, Daml-LF, Canton 3.x versions, Token Standard (CIP-0056/0112), external parties, wallets, APIs, PQS, upgrades

### Takeaway
Daml is a Haskell-derived, purely functional, strongly typed contract language whose templates declare signatories, observers and controller-gated choices; it compiles to Daml-LF, which participants interpret deterministically. The stack in late 2026 is Canton 3.7.x / Splice 0.10.x, protocol versions 36–37, Daml-LF 2.3–2.4, with a v1 and v2 token standard, externally signed parties for wallet-style custody, and SQL access via PQS.

### Cited Findings
**Language and contract model**
- **[OFFICIAL] Language properties.** "Daml is a purely functional and strongly statically typed language", "a custom language stack derived from Haskell", "designed to provide maximal confidence and safety for mission critical institutional use cases". — [Polyglot Canton whitepaper (Feb 2025)](https://www.canton.network/hubfs/Canton%20Network%20Files/whitepapers/Polyglot_Canton_Whitepaper_11_02_25.pdf)
- **[OFFICIAL] Template anatomy.** `template … with <fields> where signatory …; observer …; choice Name : ReturnType with <args> controller <party> do <updates>`. **Signatory** must authorise creation; **observer** may see; **controller** may exercise a given **choice**; **consuming** choices archive the contract, **nonconsuming** ones leave it active. Contracts are immutable: "Archive old contract, create new one". No external API calls from Daml (see external calls below). — [Core Concepts](https://docs.canton.network/overview/understand/core-concepts); [Architecture Overview](https://docs.canton.network/overview/learn/architecture)
- **[OFFICIAL] Daml-LF / DAR.** Daml-LF = "the compiled bytecode format for Daml contracts"; a **DAR** is a compiled package uploaded to (and *vetted* on) participants. — [Glossary](https://docs.canton.network/overview/understand/glossary)
- **[OFFICIAL] Contract keys returned in 3.5, weaker than 2.x.** Canton 3.5 / LF 2.3: "The keys are not unique… Negative lookups are not validated. As a consequence, application developers must ensure key uniqueness through external enforcement." — [Canton 3.5.1 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-5-1)
- **[OFFICIAL] External calls (LF 2.4, PV 36).** A choice can call a deterministic *extension service* run by the participant operator; the result is recorded in the transaction and re-checked by every confirming participant. — [External calls](https://docs.canton.network/appdev/deep-dives/external-calls)
- **[OFFICIAL] Polyglot direction.** The Feb-2025 whitepaper demonstrates Wasm engines in Canton and proposes hosting Solidity via Solang or Rust-EVM. — [Polyglot Canton whitepaper](https://www.canton.network/hubfs/Canton%20Network%20Files/whitepapers/Polyglot_Canton_Whitepaper_11_02_25.pdf)

**Versions (as of 26 Nov 2026)**
- **[OFFICIAL] Canton release ↔ protocol version (PV).** 3.3 → PV 33; 3.4 → PV 34; 3.5 → PV 34, 35; 3.6 → PV 34, 35, 36; 3.7 → PV 36, 37. Splice series: 0.4.x (Canton 3.3), 0.5.x (3.4), 0.6–0.8.x (3.5), 0.9.x (3.6), 0.10.x (3.7). — [Releases and Versioning](https://docs.canton.network/release-notes/releases-and-versioning); [Splice release notes](https://docs.canton.network/global-synchronizer/release-notes/splice)
- **[OFFICIAL] Latest releases.** Canton 3.7.5 released 25 Nov 2026; Splice 0.10.4 (bundles Canton 3.7.5). Canton 3.5.1: 27 May 2026; 3.6.1: 5 Oct 2026; 3.7.0: 29 Oct 2026. Cadence: weekly patch releases, roughly quarterly minors, ≤ 1 major per six months. — [Releases and Versioning](https://docs.canton.network/release-notes/releases-and-versioning); [Splice release notes](https://docs.canton.network/global-synchronizer/release-notes/splice)
- **[OFFICIAL] Daml-LF.** LF 2.3 introduced in 3.5 (PV 35), default compile target from 3.6; LF 2.4 with PV 36. — [Canton 3.6.1 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-6-1)

**Token standard**
- **[OFFICIAL] CIP-0056 (Final; created 7 Mar 2025, approved 31 Mar 2025).** Six APIs, each an on-ledger Daml interface plus optional off-ledger HTTP API: token metadata, holdings, transfer instruction, allocation, allocation request, allocation instruction. Roles: **registries** (asset admins), **wallets/custody**, **apps**. Supports FOP (peer-to-peer) transfers and multi-leg atomic DvP via allocations. "Inspired by ERC-20… covers all features of ERC20 except unconstrained allowances"; amounts are Daml `Decimal` (28 integer + 10 fractional digits). Registries "have full control over the structure of the workflows". — [CIP-0056](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0056/cip-0056.md)
- **[OFFICIAL] CIP-0112 Token Standard V2 (approved 12 Jun 2026).** Backward-compatible v2 packages (holding, transfer-instruction, allocation, allocation-request, allocation-instruction, transfer-events) adding privacy-enhanced batch settlement, configurable controllers/observers, account fields for multi-tier custody chains, "Delivery versus Mint/Burn". V2 endpoints are already in the OpenAPI index and in Splice 0.8.3+. — [CIP-0112](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0112/cip-0112.md); [docs index](https://docs.canton.network/llms.txt)
- **[OFFICIAL] Canton Coin compliance.** CC implements the standard; CIP-0107 (Final, Mar 2026) extended the prepare-to-execute window for CC from 10 minutes to 24 hours via an `ExternalPartyConfigState` contract. CC transfers require a receiver **preapproval** (CIP-0119 makes a 90-day base duration free). — [CIP-0107](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0107/cip-0107.md); [CIP-0119](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0119/cip-0119.md)

**External parties / external signing**
- **[OFFICIAL] Hosting permissions.** A party's `PartyToParticipant` topology mapping gives each hosting participant **Submission** (SPN), **Confirmation** (CPN) or **Observation** (OPN) rights plus a confirmation threshold. Granting Submission makes the party *internal/local*; with only Confirmation/Observation the party is *external* and its own signing keys (with their own threshold) are registered in the mapping. — [External signing](https://docs.canton.network/appdev/deep-dives/external-signing); [Local and External Parties](https://docs.canton.network/overview/reference/external-party)
- **[OFFICIAL] Flow.** *Interactive Submission Service*: `PrepareSubmission` (participant interprets and returns the transaction + hash) → wallet signs the hash offline → `ExecuteSubmission`. Default key scheme Ed25519; hashing scheme V4 covers external-call results. — [External signing](https://docs.canton.network/appdev/deep-dives/external-signing); [External calls](https://docs.canton.network/appdev/deep-dives/external-calls)
- **[OFFICIAL] Residual trust.** External signing removes trust in the validator for *authorising* transactions, but the confirming validators still validate on the party's behalf: threshold-many colluding hosting nodes could "confirm the activeness of an inactive contract and thereby spend a contract twice". Multi-hosting with threshold > 1 mitigates; decentralised parties cannot submit ordinary Ledger API commands. — [Decentralization](https://docs.canton.network/overview/reference/decentralization)
- **[OFFICIAL] PV 37 topology change.** `v31` `PartyToParticipant` replaces the onboarding flag with hosting states Nominated → Freezing → Onboarding → Active (first two "not yet fully functional"). — [Canton 3.7.0 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-7-0)

**Wallets, APIs, PQS**
- **[OFFICIAL] CIP-0103 dApp Standard (approved 29 Jan 2026).** Vendor-neutral dApp API between browser dApps and wallets. Tooling: **Wallet SDK** (TypeScript, for wallet providers/exchanges), **dApp SDK** (browser side), **Wallet Gateway** (JSON-RPC). — [CIP-0103](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0103/cip-0103.md); [SDKs & Tools overview](https://docs.canton.network/sdks-tools/overview)
- **[OFFICIAL] Ledger API.** gRPC (Protobuf) and JSON (HTTP, `/v2/...`) variants: command submission, update/transaction streams, active contract set, completions; separate Admin API per node. Splice adds Scan, Scan-proxy, validator and token-standard HTTP APIs (OpenAPI). — [Architecture Overview](https://docs.canton.network/overview/learn/architecture); [docs index](https://docs.canton.network/llms.txt)
- **[OFFICIAL] PQS (Participant Query Store).** Optional component that projects a participant's ledger data into PostgreSQL for SQL queries and long-term history. — [Glossary](https://docs.canton.network/overview/understand/glossary); [Pruning](https://docs.canton.network/overview/reference/pruning)
- **[OFFICIAL] Scale limits.** Participant supports "up to 1 million parties per node"; the validator *app* currently supports only ~200 onboarded parties (workarounds exist). PV 37 caps: 100 hosting participants per party, 10,000 recipients per envelope, 20 signing keys per entity. — [Network Scalability](https://docs.canton.network/global-synchronizer/production-operations/scalability); [Canton 3.7.0 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-7-0)

**Smart-contract upgrades (SCU)**
- **[OFFICIAL]** SCU lets authors publish new package versions "without any downtime for package users and existing contracts"; packages are referenced by *package name* rather than only package ID. Allowed: adding `Optional` fields/choice parameters at the end, new choices, changed choice bodies/controllers, changed `ensure`, new interface instances. Not allowed: renames, field type/order changes, deletions, changing signatories/observers results for existing contracts, changing interfaces or exceptions, switching consuming ↔ non-consuming. Checked at compile time, DAR upload and runtime. — [Smart Contract Upgrade](https://docs.canton.network/appdev/deep-dives/smart-contract-upgrade)

### Inferences
- Upgrades are stakeholder-governed: there is no proxy/admin-key pattern; a new package version must be vetted by the participants involved, and immutable signatory sets mean an upgrade cannot silently change who controls existing contracts.
- The token standard pushes significant functionality off-ledger (registry HTTP APIs for UTXO disclosure, metadata, total supply) — a direct consequence of having no global state.

### Gaps
- The Version Compatibility Dashboard (per-network deployed versions; "Last Updated: November 24, 2026") is rendered client-side and its tables could not be read.
- A consolidated, sourced list of production wallets supporting CIP-0103 was not gathered (outside technical scope; ecosystem researcher may cover).

### Inferences
- All external connectivity is attestation-based (Circle attester, LayerZero DVNs, Chainlink DONs). Because Canton has no global state root, an external chain cannot verify Canton state with a light client; a Canton-side contract involving the bridge operator's party is the anchor. This is a structural limit, not an implementation gap.
- Interop providers receiving SV reward weight creates an incentive alignment (and a potential conflict of interest) that is unusual among L1s.

### Gaps
- No evidence found of any ZK light-client, validity-proof or "public verifiability" implementation for Canton beyond Rooz's statement of intent.
- Wormhole: SV weight granted (CIP-0065) but no confirmation of a live Canton integration was found. USDT0 live status on Canton unconfirmed.
- Production status of Chainlink CCIP on Canton MainNet and of Zenith MainNet could not be verified.

## 8. Performance and scalability (throughput, finality, horizontal scaling, traffic model, bottlenecks)

### Takeaway
There is no official TPS benchmark for the Global Synchronizer. Officially reported usage is ~1.7 million transactions/day (≈ 20 TPS average, Nov 2026). The scaling claim is horizontal (more synchronizers and participants, no global replication), while per-synchronizer ordering, per-contract contention and a high byte-based fee (US$60/MB, ≈ US$1 per typical transaction) are the practical limits.

### Cited Findings
- **[OFFICIAL] Usage figures.** "Canton currently handles ~600 million annualized transactions (~1.7 million each day), including $9T of tokenized real-world assets processed monthly"; "more than 150 production applications… more than 830 firms" (Nov 2026 blog). Dec 2025: ~600 nodes upgraded in under 24 h (up from ~200 nodes in July 2025). — [canton.network blog "One Giant Leap"](https://www.canton.network/blog/one-giant-leap); [canton.network blog on the 3.4 upgrade](https://www.canton.network/blog/canton-upgrades-amid-accelerating-demand)
- **[OFFICIAL] Horizontal-scaling claim.** "The Canton protocol allows each application to scale independently"; the FAQ: "Capacity is increased with every new participant or operator that chooses to spin up a subnetwork"; "No single node processes all network transactions." Validation load "is bounded by the number of stakeholders, not by the total number of nodes". — [Canton Network whitepaper](https://www.canton.network/hubfs/Canton/Canton%20Network%20-%20White%20Paper.pdf); [canton.network FAQ](https://www.canton.network/faq); [Smart Contract Consensus](https://docs.canton.network/overview/reference/smart-contract-consensus)
- **[OFFICIAL] Finality.** Deterministic at the sequenced mediator verdict; docs call it "immediate". No published latency SLO. — [Smart Contract Consensus](https://docs.canton.network/overview/reference/smart-contract-consensus)
- **[OFFICIAL] Latency guidance.** Docs' worked example assumes ~750 ms transaction latency and derives ~67 settlements/s for a contended resource with `max_settlements = 50`; an async submission is said to take 50–1000 ms depending on command size. — [Performance optimization](https://docs.canton.network/appdev/deep-dives/performance-optimization)
- **[INDEPENDENT][SNIPPET] Community load test.** A developer benchmarking a CIP-0056 `TransferFactory_Transfer` through one participant measured ~15 transfers/s, median ≈ 400 ms, p99 ≈ 1.2 s, plateauing at ~22/s offered; the post also mentions 30–31 transactions committed within one second by a participant on MainNet. — [Canton forum](https://forum.canton.network/t/load-performance-testing-for-canton-apps-early-results-benchmarking-a-token-standard-registry/9047)
- **[INDEPENDENT][SNIPPET]** Chainspect lists no finality/TPS data for Canton; one third-party page claims a ~7 TPS peak without method. — [Chainspect](https://chainspect.app/compare/canton-vs-avalanche)
- **[OFFICIAL] Traffic (bandwidth) model.** Every message a participant submits for sequencing consumes *traffic* in bytes; "the sending validator is charged; recipients are not". Two balances per participant: a free regenerating **base rate** (`burstAmount` bytes per `burstWindow`) consumed first, then **extra traffic** bought by burning CC at `extraTrafficPrice` USD/MB. Cost = payload bytes × (1 + recipients × `readVsWriteScalingFactor`/10,000). When both are exhausted the sequencer rejects submissions. SV participants and mediators have unlimited traffic. — [Tokenomics of the GS](https://docs.canton.network/overview/reference/tokenomics-of-gs); [Synchronizer traffic](https://docs.canton.network/global-synchronizer/deployment/synchronizer-traffic)
- **[OFFICIAL] Parameter values.** Docs example (DevNet tab, Splice 0.10.3): `burstAmount` 400,000 bytes per `burstWindow` 1,200 s (20 min); `extraTrafficPrice` 60.0 USD/MB; `readVsWriteScalingFactor` 4; `minTopupAmount` 200,000 bytes. CIP-0129 confirms MainNet list price: "currently $60/MB, about $1 for a typical transaction before rewards" and calls this "too high" a barrier for payments/trading. — [Synchronizer traffic](https://docs.canton.network/global-synchronizer/deployment/synchronizer-traffic); [CIP-0129](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0129/cip-0129.md)
- **[OFFICIAL] What counts as traffic.** Confirmation requests, confirmation responses, topology transactions, periodic ACS commitments. CIP-0104 (approved 27 Oct 2026) proposes making protocol-conformant confirmation responses free so validators pay only for submissions. — [Synchronizer traffic](https://docs.canton.network/global-synchronizer/deployment/synchronizer-traffic); [CIP-0104](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0104/cip-0104.md)
- **[OFFICIAL] Fees beyond traffic.** CIP-0078 (Sept 2025) set CC transfer/create/lock fees to 0; a per-UTXO holding fee remains. Mining rounds open every 10 minutes (~52,560/yr). — [CIP-0078](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0078/cip-0078.md); [Tokenomics of the GS](https://docs.canton.network/overview/reference/tokenomics-of-gs)
- **[OFFICIAL] Known bottlenecks / fixes.**
  - Single-leader CometBFT ordering → replaced by multi-leader CantonBFT (2026). — [Canton 3.5.15 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-5-15)
  - ACS-commitment memory grew with parties/stakeholder groups → redesigned in PV 36 "to lift party growth restrictions on the network". — [Canton 3.6.1 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-6-1)
  - Contention: UTXO contracts can be consumed once; automatic reassignment "can cause unexpected contention". — [Reassignment Protocol](https://docs.canton.network/overview/reference/reassignment-protocol)
  - Validator-app limit of ~200 parties per validator. — [Network Scalability](https://docs.canton.network/global-synchronizer/production-operations/scalability)
  - Upgrade downtime: pre-LSU protocol upgrades paused the network for "90 minutes to 3 hours"; LSUs cut Daml downtime to "dozens of seconds" but topology changes still freeze "up to a few hours". — [CIP-0117](https://raw.githubusercontent.com/canton-foundation/cips/main/cip-0117/cip-0117.md); [Canton 3.5.1 release notes](https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-5-1)
  - SV storage: default CometBFT volume was raised from 1,250 Gi to 2,500 Gi during its lifetime. — [Splice release notes](https://docs.canton.network/global-synchronizer/release-notes/splice)

### Inferences
- 1.7 M tx/day ≈ 19.7 TPS average (600 M/yr ≈ 19.0 TPS). This is an *average of reported activity*, not capacity; an unknown share is automated reward/round activity rather than user business transactions.
- US$60/MB with "≈ US$1 per typical transaction" implies a typical transaction consumes roughly 16–17 kB of sequenced traffic — far heavier than an EVM transfer, because views, root-hash messages, confirmations and results are all sequenced.
- "Unlimited horizontal scalability" is true for workloads that can be partitioned onto separate synchronizers; any workflow requiring atomic composition must share one synchronizer and is bound by that synchronizer's ordering throughput (and, on the GS, by price).

### Gaps
- No official, reproducible TPS/latency benchmark for the Global Synchronizer or for CantonBFT.
- MainNet values of traffic parameters other than the US$60/MB price were not verified (Scan API not reachable).
- Share of daily transactions that is organic vs. reward-driven automation is unknown.

### Inferences
- The five RFQ areas map exactly onto the components introduced or exposed in 2026 (CantonBFT orderer, LSU machinery, crypto layer, public sequencer API, Ledger/JSON API) — i.e. CantonBFT and LSU went to MainNet **before** an independent third-party audit under this programme was commissioned.
- Absence of public incidents is weak evidence: by design, most application-level failures on Canton would be visible only to stakeholders.
- Having Digital Asset (the code's author) among the evaluators of auditors is a governance point worth noting for independence.

### Gaps
- Dev Fund Proposal #410 and the milestone issues (#499–#504) live on github.com and could not be read; the names of the other six of the "11 critical areas", budgets and any earlier core-protocol audit reports are unknown.
- No public, complete list of historical third-party audits of the Canton protocol or Splice core was found.

## 12. Substantive technical criticisms and the responses

### Takeaway
The serious criticisms are architectural, not rhetorical: (1) no single shared ledger/global state, hence no public verifiability; (2) a small, vote-admitted ordering set; (3) integrity rests on honest mediators and on each party's own validator; (4) privacy is operational (data not shared) rather than cryptographic; (5) composability is bounded by a common synchronizer; (6) data can be pruned. Digital Asset's replies: users only ever trust their own validator; regulated assets are permissioned anyway; ZK is too immature for systemically important finance; public verifiability is planned.

### Cited Findings
- **Criticism 1 — "Not a real blockchain" / no shared ledger.** Alex Gluchowski (Matter Labs): a blockchain's core feature is "a single shared ledger" enforcing rules for everyone at once; "On Canton, you rely solely on the multisig. On Ethereum, you rely on smart contracts that are enforced by the network." — **[SNIPPET][INDEPENDENT, competitor]** [Cointelegraph, 21 Apr 2026](https://cointelegraph.com/news/canton-zksync-clash-blockchains-enforce-rules)
  - **Response.** Kfir: correct that Canton has no global shared state, "incorrect in implying that this negatively affects Canton's trust model… I only trust my own validator and assume anyone else can be malicious"; critics are "confusing the capabilities of Canton" with how centralised RWA issuers use it. Rooz: public-chain users also depend on trusted issuers (e.g. USDC freezes); he calls loud critics "crypto ideologues". — **[SNIPPET]** [Cointelegraph](https://cointelegraph.com/news/canton-zksync-clash-blockchains-enforce-rules); [DL News](https://dlnews.com/articles/defi/canton-network-ceo-addresses-criticism-from-crypto-ideologues/)
  - **Docs agree on the fact:** "The Global Synchronizer is not a separate blockchain… not a separate storage layer". — **[OFFICIAL]** [The Global Synchronizer](https://docs.canton.network/overview/understand/global-synchronizer)

### Inferences
- Both sides agree on the facts; the dispute is definitional (is global verifiability essential to "blockchain"?) and about threat models. For an institution whose counterparties are known and legally accountable, Canton's model (trust own node; counterparties cannot commit invalid state involving you; ordering by a BFT consortium) is coherent. For an outside holder who wants to verify an asset's total supply or an issuer's solvency without being a stakeholder, Canton today offers no cryptographic assurance.
- The strongest independent point is L2BEAT's: confidentiality is protected *from* infrastructure, integrity is delegated *to* infrastructure and hosting nodes. The strongest Canton point is that this mirrors how regulated assets are enforced anywhere (issuer control), while avoiding ZK implementation risk.
